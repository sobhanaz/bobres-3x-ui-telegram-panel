# Phase 1 Design: First Sellable Slice

## Goal

Build the first installable, sellable slice of BOBRES: a Telegram bot + web dashboard that lets an operator sell 3x-ui (Xray) VPN subscriptions. Phase 1 ends with a one-command install on Ubuntu/Debian that runs four service containers + Caddy and supports:

- User registration via Telegram `/start` with language selection (fa/en).
- Plan catalog (traffic-limited and time-only plans) with IRT primary pricing and optional USDT.
- Wallet top-up with manual approval of crypto TXID and bank/card receipt submissions.
- Plan purchase auto-debiting wallet if balance is sufficient, otherwise manual payment.
- Free trial: one per Telegram ID.
- Subscription provisioning through 3x-ui v3.x API (create client, attach to enabled inbounds, deliver link + QR).
- Admin dashboard (Vue 3 embedded in `core`) for manual payment review, plan management, users, subscriptions, servers, branding/texts, and audit log.

## Scope Boundaries

### In Scope

- Four service binaries: `core`, `bot`, `payments`, `provisioner`.
- Postgres transactional outbox in each schema; consumers pull it over gRPC (see PLAN.md §11, 2026-10-03).
- gRPC for synchronous service-to-service calls (service-token auth).
- Manual payment providers: wallet, manual-card-receipt, manual-crypto-TXID.
- Bot: long polling by default; webhook mode supported.
- Dashboard: full Vue 3 + Vite + TypeScript embedded in `core` via `embed.FS`.
- Dashboard auth: password + optional TOTP + Telegram Login Widget.
- Roles: owner, admin, support, reseller (reseller UI minimal in Phase 1).
- One-command install via `install.sh` + Docker Compose.

### Out of Scope

- Automated gateways: Zarinpal, Telegram Stars, third-party crypto, chain watcher.
- Renewal / traffic top-up flows.
- Referrals, discount codes, resellers full UI.
- Notifications / notifier service (bot sends immediate messages only).
- Multi-server 3x-ui support (schema supports it, but only one server in UI).
- Backups/restore drill, monitoring stack, license server.
- Public end-user web portal.

### Service Responsibilities

| Service | Owns | Calls |
|---|---|---|
| `core` | Users, plans, orders, wallet ledger, subscriptions, audit log, branding/settings, dashboard API + SPA. | `payments.CreateIntent`, `payments.ReviewReceipt` (dashboard), `provisioner.CreateClient`, `provisioner.RenewClient`. |
| `bot` | Telegram handlers, inline keyboards, i18n, rate limits. | `core` gRPC only. |
| `payments` | Payment intents, manual receipts, wallet debit, ledger credit entries in `payments` schema. | Emits `payment.succeeded`/`failed`/`expired` via outbox. |
| `provisioner` | 3x-ui servers, provision jobs, client map, 3x-ui API adapter. | Emits `subscription.provisioned`/`provision_failed` via outbox. |

## Cross-Service Communication

### Synchronous (gRPC)

- Internal network only; Caddy does not expose gRPC ports publicly.
- Auth: `Authorization: Bearer <service-token>`; tokens generated by installer.
- `core` acts as orchestrator: it calls `payments` and `provisioner` and waits for synchronous confirmations, then publishes domain events to its own outbox.

### Asynchronous (Postgres Outbox + gRPC pull feed)

> 2026-10-03: the LISTEN/NOTIFY + shared-table relay described below was replaced: a service never reads
> another service's schema (per-service roles forbid it, and payments may run elsewhere). Consumers pull
> `events.v1.EventFeedService` with per-consumer cursors, de-duplicate on UUID event ids, retry with backoff
> and dead-letter what cannot be applied.

- Every schema has `outbox` and `inbox` tables.
- `core` publishes `order.created`, `order.paid`, `subscription.provisioned`, etc.
- `payments` and `provisioner` consume relevant `core` events and publish their own events.
- Phase 1 keeps the event bus simple: each service has a poller that reads its local outbox and forwards via `LISTEN/NOTIFY` to local consumers; remote consumers poll their schema's outbox or use a small relay.

### Event Catalog (Phase 1)

| Event | Producer | Consumers | Purpose |
|---|---|---|---|
| `user.registered.v1` | core | bot | Welcome message, referral handling (later) |
| `order.created.v1` | core | payments | Create payment intent |
| `wallet.debited.v1` | core | payments | Wallet order fully paid synchronously |
| `payment.succeeded.v1` | payments | core | Manual payment approved; mark order paid |
| `payment.rejected.v1` | payments | core | Manual payment rejected; cancel/expired |
| `order.paid.v1` | core | provisioner | Trigger provisioning |
| `subscription.provision_requested.v1` | core | provisioner | Explicit create/renew command |
| `subscription.provisioned.v1` | provisioner | core, bot | Deliver link + QR |
| `subscription.provision_failed.v1` | provisioner | core, bot | Alert admin, retry later |
| `wallet.credited.v1` | payments | core, bot | Top-up approved; notify user |

## Money Rules

- All amounts are `bigint` minor units. IRT scale = 0 (Toman, no decimals). USDT scale = 6.
- `wallets.balance` is a cache maintained in the same transaction as `ledger_entries`.
- `ledger_entries` is append-only; no `UPDATE`/`DELETE`.
- Every money call carries an `idempotency_key` (UUID v7) with a unique index.
- Wallet balance cannot go below 0 (DB `CHECK`).
- Trial grants are recorded in `ledger_entries` with `kind = 'trial_grant'` and amount 0.

## Purchase / Trial Flows

### Free Trial

1. User taps "Free trial" in bot.
2. `core` checks `users` for existing trial subscription; if none, creates an `order` with `type = new`, `status = active`, `amount = 0`, links to a trial `plan`.
3. `core` calls `provisioner.CreateClient` synchronously (trial is instant).
4. On success, bot sends subscription link + QR.

### Wallet Order

1. User selects plan.
2. `core.CreateOrder` returns order.
3. If wallet balance >= amount, `core` immediately debits wallet, sets `status = paid`, emits `order.paid`.
4. `core` calls `provisioner.CreateClient`, updates `subscriptions`.
5. Bot delivers link.

### Manual Payment Order

1. User selects plan, payment method "manual card" or "manual crypto".
2. `core.CreateOrder` sets `status = awaiting_payment`, emits `order.created`.
3. `payments` creates `payment_intent` with instructions (card number / crypto address + reference/amount).
4. Bot shows instructions; user submits receipt photo + reference or TXID + network.
5. `payments` updates `manual_receipts` and sets intent `status = confirming`.
6. Admin sees queue in dashboard, approves or rejects with reason.
7. On approve: `payments` writes a `topup` credit to `payments.ledger_entries`, emits `payment.succeeded`.
8. `core` marks order `paid`, writes a `purchase` debit to `core.ledger_entries`, updates `wallets.balance` if wallet was used (not needed for manual-only orders), emits `order.paid`.
9. `core` calls `provisioner.CreateClient`; bot delivers link.

### Wallet Top-Up

1. User chooses amount and manual provider.
2. `payments.CreateIntent` (no order_id) with `kind = topup`.
3. User submits receipt/TXID.
4. Admin approves.
5. `payments` writes a `topup` credit to `payments.ledger_entries`, emits `wallet.credited`.
6. `core` writes a matching `topup` credit to `core.ledger_entries`, updates `wallets.balance`.
7. Bot sends balance update message.

## Dashboard (Phase 1 Pages)

1. **Login**: password + optional TOTP; Telegram Login Widget button (only shown when a domain is configured; falls back to password-only otherwise).
2. **Overview**: new users today, active subscriptions, pending manual payments, server health.
3. **Plans**: list, enable/disable, create/edit (name fa/en, kind, duration, traffic, price IRT/USDT, trial flag, sort).
4. **Orders**: filter by status, view detail, retry provisioning for `provision_failed`.
5. **Manual Payment Queue**: approve/reject receipts and TXIDs with reason.
6. **Users**: search by telegram_id/username, view profile + wallet + orders + subscriptions.
7. **Subscriptions**: list, disable, reset traffic, resync from 3x-ui.
8. **Servers**: add/edit 3x-ui panel URL + API token (write-only, encrypted), test connection, list enabled inbounds.
9. **Branding & Texts**: bot name, welcome text fa/en, support contact, currency, card info, crypto addresses, colors/logo.
10. **Audit Log**: filterable list of actions with actor and reason.

## 3x-ui Integration

- Only `provisioner` holds the panel API token (encrypted at rest with install master key).
- Adapter interface `PanelAdapter`: `CreateClient`, `RenewClient`, `DeleteClient`, `ResetTraffic`, `GetUsage`, `GetLinks`, `ListInbounds`, `HealthCheck`.
- First implementation targets 3x-ui v3.x via Bearer token.
- Startup: detect panel version, warn if outside tested range.
- Per-client mutex because `clients/update` replaces the row.
- Client email format: `u{telegram_id}-{short_order_id}`.
- New clients attach to all enabled inbounds returned by `ListInbounds`.

## Security

- Secrets at rest encrypted with install master key (envelope).
- Service-token auth on gRPC; no mTLS in Phase 1.
- Dashboard: secure cookies, CSRF, rate limits, argon2id passwords, optional TOTP, Telegram Login Widget signature verification.
- Input validation on every admin form; audit log on every write with actor + reason.
- Manual receipt review requires admin role.
- Bot rate limits per Telegram ID.
- 3x-ui URL must be HTTPS; private IP ranges blocked unless explicitly allowed.

## Testing Strategy

- Unit tests for domain logic (wallet, orders, trial eligibility).
- Fake 3x-ui server in `internal/xuifake` for provisioner tests.
- Real 3x-ui integration tests behind build tag `integration` requiring `XUI_TEST_URL` and `XUI_TEST_TOKEN`.
- gRPC contracts tested with buf + generated Go code.
- End-to-end install test in CI with Docker Compose.
- Manual payment flow tested with fake receipt/TXID and dashboard approval.

## Installer / Deployment

- `install.sh` asks for: domain, bot token, admin Telegram ID, DB password, 3x-ui URL + token.
- Generates `.env`, master encryption key, service tokens.
- Runs `docker compose up -d` with Caddy, Postgres, Redis, core, bot, payments, provisioner.
- First admin is seeded from installer input.
- Health/ready endpoints on every service.
- CI: lint, unit tests, integration tests (when secrets present), image build + sign.

## Risks

- Building full Vue dashboard in Phase 1 adds significant frontend work and may delay install.
- True microservices add ops complexity; installer must handle inter-service discovery.
- 3x-ui API changes frequently; adapter tests only cover v3.x.
- Manual payment fraud relies on admin diligence; automated gateways reduce risk later.
- Service-token auth without mTLS is acceptable for single-host compose but must be upgraded before multi-host.

## Non-Goals

- Public marketing site, end-user web portal.
- Automated payment gateways.
- Referrals, discount codes, resellers full UI.
- Notification scheduler service.
- License server / update channel.
- Kubernetes Helm chart.
